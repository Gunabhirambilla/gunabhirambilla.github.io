Hourly Slack Alerting on a Laggy Siebel CRM View
Siebel CRMSQLPythonSlack API
Hourly polling against a reporting view with multi-hour lag, diffed against last-seen state. Used by 15 Commercial Ops teammates; they stopped missing new cases, replies, and assignments.
+
The Problem

The Siebel CRM reporting view Commercial Ops relied on lagged live case activity by several hours. New cases, customer replies, and assignments all sat invisible until someone happened to refresh a dashboard — there was no push notification layer on top of a CRM never built for one.

Adoption
Used by15 Commercial Ops teammates
BeforeNew cases, replies and assignments sat invisible until someone refreshed a lagging Siebel view
NowAbout 2 alerts a day, sent only when something new needs attention
DecisionWidened the lookback window from 60 to 720 minutes after tracing missed alerts to a roughly 4.5-hour lag in the source view, instead of just retrying.
IncidentA mid-run crash re-sent 17 alerts. Fixed by saving the watermark after every send, disabling job retries and seeding the 17 already sent.
How it's built

Built an hourly polling job against the lagging view that diffs against a last-seen cursor to detect genuinely new activity by type — new case, customer reply, or assignment — then posts formatted alerts to the right Slack channel. The job is designed around the view's inherent staleness rather than fighting it.

Technical Details
  • Last-seen cursor prevents duplicate alerts across runs
  • Classifies activity into new case / reply / assignment before routing
  • Slack webhook integration with channel-specific formatting
  • Tolerant of the CRM's multi-hour reporting lag by design
  • Runs hourly on a schedule, no manual trigger required

Tiered Diagnostic Notebook for Fleet Telemetry Support
PythonSQLLLM
Three escalating tiers — deterministic rules first, AI case notes only when needed. Used daily by 15 analysts; time per case dropped from ~45 to ~10 minutes, roughly 50 analyst-hours saved a day.
DecisionFixed decision tree first, deep-dive cells only when the verdict calls for them, and the LLM last. Most cases resolve on the cheap, predictable path.
+
The Problem

Support analysts needed to diagnose why a vehicle wasn't reporting telemetry, but root causes ranged from a simple connectivity gap to a multi-system fault. Running an LLM against every case was slow, costly, and unnecessary for the majority that a straightforward rule check could already explain.

Adoption
Used by15 support analysts, daily (~6 cases each)
BeforeAbout 45 minutes per case, querying several backend systems and navigating the CRM by hand
NowAbout 10 minutes per case, roughly 50 analyst-hours saved a day, with AI notes only when the case needs them
How it's built

Structured the notebook as three escalating tiers: Tier 1 runs fast, deterministic SQL checks against the most common known failure patterns; Tier 2 adds cross-table correlation for less obvious cases; Tier 3 — AI-generated case notes — only fires for cases that survive both earlier tiers unresolved, summarizing the diagnostic trail for the analyst instead of leaving them to piece it together.

Technical Details
  • Tier 1: deterministic SQL rule checks for common failure signatures
  • Tier 2: cross-table correlation for subtler fault patterns
  • Tier 3: LLM-generated case notes, gated to unresolved cases only
  • Diagnostic trail logged per case for auditability
  • AI cost scoped to the minority of cases that actually need it

Self-Serve Case Queue Report Built on Two Window Functions
SQLQUALIFYWindow Functions
One parameter, three real-time queues, no Python and no dashboard team. Used by 15 analysts about 4 times a day, and picked up by the Level 3 team.
+
The Problem

Analysts had no consolidated, real-time answer to three questions: what needs a response now, what's gone stale without follow-up, and what's the full state of everything still open. The data was all in the CRM — it just wasn't shaped for triage, and auto-acknowledgment emails made "needs response" counts noisy.

Adoption
Used by15 analysts (~4 times a day) and the Level 3 team
BeforeManual navigation of the CRM to piece together each queue
NowThree real-time queues from one cloned notebook, no dashboard team
DecisionPure SQL, cloned per analyst rather than one shared notebook, so no analyst’s run affects another’s and non-engineers can maintain it.
How it's built

A pure-SQL notebook driven by a single :analyst_name parameter, cloned per analyst for isolated execution state. A UNION bridges current case status with full historical activity, and ROW_NUMBER / QUALIFY isolate the most recent activity per case without subquery nesting. Auto-acks are filtered by treating a short-window inbound right after an outbound as system-generated, and pure-SQL weekday arithmetic powers business-day stale-follow-up flags with no UDF or calendar table.

Technical Details
  • Single string parameter makes the notebook portable across analysts
  • QUALIFY replaces nested subqueries for "most recent per case"
  • Auto-acknowledgment filtering keeps "needs response" counts honest
  • Pure-SQL business-day arithmetic, no UDFs or calendar table
  • Inline CASE expressions derive urgency tiers automatically

RAG Case Analysis & Case-Note Generator on Databricks
DatabricksPythonVector DBEmbeddings
Retrieval-augmented case analysis and note generation over CRM case history and vehicle telemetry, with a validation layer that catches stale, duplicate, or contradictory records before they reach the LLM. Used by 15 analysts; notes go out as generated, saving ~25 minutes each.
+
The Problem

Case analysis and note generation are only as trustworthy as the records they retrieve from. Stale case history, duplicate or contradictory CRM entries, and telemetry that disagrees with what a case note says all silently corrupt LLM output downstream — with no easy way to detect the failure after the fact.

Adoption
Used by15 analysts
BeforeWriting each case note by hand from CRM history and telemetry
NowNotes generated from validated records and sent as generated
How it's built

Built the retrieval layer on Databricks over CRM case history and telemetry data, powering case analysis and a case-note generator. A quality framework runs on the source records before embedding: freshness checks (last-updated thresholds), deduplication (semantic similarity clustering), contradiction detection across records, and provenance tagging. Records that fail are quarantined; the rest enter the vector index with quality metadata attached.

Technical Details

  • Semantic dedup via embedding similarity clusters
  • Cross-record contradiction detection (case history vs. telemetry)
  • Provenance metadata propagated to retrieval layer
  • Retrieval feeds case analysis and case-note generation
  • Quarantine queue for human review

Idempotent Incremental ETL Framework
SnowflakeSQLPython
Watermark tracking, merge upserts, late-arriving data validation, control tables for recovery. Daily pipelines hardened for safe reruns.
+
The Problem

Daily pipelines occasionally failed mid-run or produced duplicates after partial recovery. Engineers had to manually clean state before reruns, and late-arriving source records silently corrupted aggregates. Trust in the data was eroding.

The Approach

Designed an incremental framework around three principles: deterministic watermark tracking, merge-based upserts (never plain inserts), and explicit validation gates. Every run logs to a control table; every failure can be safely retried without manual cleanup.

Technical Details
  • Watermark column tracked per source-target pair
  • MERGE statements with deterministic match keys
  • Validation queries for duplicates and gaps
  • Late-arriving record detection & backfill logic
  • Control tables track state for surgical recovery

// 06 · principles · 8 rules

How I think.

Opinions earned shipping data systems. Each one has a scar behind it — a 3 a.m. page, a quarter-end mismatch, a dashboard that lied for two months before anyone noticed. I write them down so I don't forget.

01 · grain
// design

If you can't state the grain in one sentence, the model isn't ready.

Most analytics bugs aren't typos. They're cardinality surprises hiding in a vague join. Pin the grain first, write SQL second. Twenty minutes of sketching saves four hours of debugging.

02 · idempotency
// pipelines

A pipeline that needs human cleanup to retry is not a pipeline.

It's a script with a person attached. Watermarks, merge upserts, control tables — make rerunning safe by construction. The first time a 3 a.m. failure becomes a 3:02 a.m. retry, you'll know it's working.

03 · isolation
// multi-tenant

There's no "mostly correct" in tenant isolation.

The row policy either holds for every query or it doesn't. Test isolation like a security control — write queries that try to violate it and confirm they can't. The worst-case bug is silent.

04 · reconciliation
// governance

Reconciliation isn't a project. It's a control plane you operate.

Run it daily, review weekly, audit monthly. Drift compounds; cadence catches it early. By month-end, three systems disagreeing has cost real money. Make every mismatch visible within 24 hours.

05 · documentation
// craft

The next engineer is a stranger.

Write SQL, comments, and docs like the person debugging this at 3 a.m. has zero context. Eventually they will. That stranger might be future you. The empathy is the same.

06 · latency
// reliability

A source that's always a few hours behind isn't broken — it's a contract you design around.

Fighting a laggy upstream system to make it feel real-time is a losing game. Diff against last-seen state, alert on what actually changed, and let the lag be a known quantity instead of a surprise someone discovers at 9 a.m.

07 · escalation
// judgment

Not every case needs an LLM. Most need a rule that already knows the answer.

Run the cheap, deterministic check first. Reserve the expensive model for whatever survives it unresolved. Tiering isn't a cost hack — it's what keeps the expensive tool's output trustworthy on the cases where it actually runs.

08 · tooling
// pragmatism

The right amount of tooling is the amount the problem actually needs.

A notebook with one parameter and two window functions can outperform a pipeline with a scheduler, a queue, and a dashboard nobody asked for. Match the architecture to the audience, not the resume.
